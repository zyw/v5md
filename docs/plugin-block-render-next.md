## 1. 二期 A：插件扩展 micromark / mdast 语法

### 1.1 背景

一期载体固定为 **fenced code + `lang`**。若要支持「看起来不像代码围栏」的块语法（例如自定义容器、短码、特殊行首标记），必须让插件介入解析，而不能只注册渲染器。

可行性边界原文：插件改解析器语法（micromark 扩展）——可作二期。

### 1.2 建议范围

- [ ] 在 `@v5md/core`（或 view 的 parse 入口）定义**只读的解析扩展挂载点**，例如：
  - 注册 micromark 扩展 / mdast 转换
  - 明确扩展的生命周期：随编辑器实例安装 / 卸载
- [ ] 约定扩展产出的节点如何进入现有渲染：
  - **方案甲（推荐先做）**：扩展仍归一成 `code` + 约定 `lang`（或 `meta`），继续走现有 Block Renderer
  - **方案乙**：扩展产出新 `MdNode.type`，再对接渲染（与「新增 AST 类型」重叠，升为三期）
- [ ] 文档化：扩展不得改写无关节点；冲突策略（同名语法、安装顺序）
- [ ] 至少一个官方示例扩展（可用极简语法，如 `:::note` → 映射到 `lang: note` 围栏等价物，或仅演示挂载）
- [ ] 测试：安装扩展后 parse 结果稳定；卸载后回退；两篇文档互不影响

### 1.3 验收标准

- 不装扩展时，现有 Markdown 往返与一期行为一致。
- 扩展可按编辑器实例安装 / 卸载，无全局污染。
- 扩展作者无需 fork `@v5md/core` 即可增加一种可被 Block Renderer 消费的语法（至少方案甲）。
- 有失败模式：扩展 `setup` 抛错时安装回滚，错误可观测。

### 1.4 依赖与风险

| 风险 | 对策 |
| --- | --- |
| micromark 扩展 API 复杂、易破坏偏移 | 强制单测覆盖 `start`/`end`；禁止「猜偏移」 |
| 与 GFM / 数学 / YAML 冲突 | 官方扩展矩阵表；冲突则安装失败 |
| 诱导过早上方案乙（新 AST） | 二期默认只批方案甲 |

### 1.5 建议切片

1. 设计挂载点 RFC（半页～一页）并评审  
2. 实现注册 / 卸载 + 单测骨架  
3. 示例扩展 + playground 开关  
4. README / `plugin-block-render.md` 交叉引用

## 2. 二期 B：补齐 `V5mdBlockRenderer.match` 的测试与文档

### 2.1 背景

§0 已冻结 `match?(node)` 与匹配优先级。实现上 `BlockRendererRegistry.resolve` **已按「先 match（安装序）→ 再 lang」查找**，安装期也允许「仅 match、无 lang」。二期要做的是把行为钉死在测试与文档上，并清掉「一期可忽略 match」的过时表述。

### 2.2 建议范围

- [ ] 核对 `packages/view/src/editor/blocks.ts` 与 §0.4 逐步一致（含空 lang + 仅 match）
- [ ] 单测覆盖（建议放在 `blocks.test.ts`）：
  - 仅 lang
  - 仅 match（无 lang）
  - 同一节点 match 与 lang 均可命中时走 match，且先安装者优先
  - 两插件 match 都为 true 时取先安装者
  - 卸载后不再命中；回退为默认代码块
- [ ] 插件作者文档：一段可复制的 `match` 示例（例如按 `node.meta` 或源码特征命中）
- [ ] 更新 `plugin-block-render.md`：删除「一期可忽略 match」；状态改为已落地

### 2.3 验收标准

- 上述用例全绿，失败信息可读。
- 现有 echarts / mermaid / mindmap（只声明 `lang`）回归不变。

### 2.4 依赖与风险

| 风险 | 对策 |
| --- | --- |
| `match` 过宽误抢其它块 | 文档强调 match 应尽量窄；用抢注用例锁行为 |
| 文档与实现再次漂移 | 测试即规范；改 resolve 必须改测 |

### 2.5 建议切片

1. 补测试（优先）  
2. 改文档表述 + README 示例  
3. 若发现实现与 §0.4 不符，再开缺陷修复 PR

## 3. 二期 C：导出快照 `snapshot()`（或等价 API）

### 3.1 背景

`@v5md/plugin-export` 依赖当前 DOM。Canvas 类块（ECharts）在导出瞬间可能尚未 hydrate 完，或需要更高清位图。一期不强制快照 API。

### 3.2 建议范围

- [ ] 在 `V5mdBlockRenderer`（或平行接口）增加可选方法，例如：
  - `snapshot?(ctx): Blob | string | HTMLElement | Promise<…>`
  - 或宿主侧 `editor.snapshotBlocks(): Promise<…>` 统一调度
- [ ] 约定导出插件在截图 / PDF 前：
  - 等待未完成的 `hydrate`
  - 对声明了 snapshot 的块优先用快照替换预览槽
- [ ] ECharts 官方插件实现 canvas → PNG（或保留 DOM 若已足够）
- [ ] Mermaid / Mindmap：SVG 已可序列化时可 no-op 或返回内联 SVG
- [ ] 测试：hydrate 未完成时导出不空白；过期 hydrate 不污染快照

### 3.3 验收标准

- 含 ECharts 的文档导出 PDF/图片时，图表可见且非占位文案。
- 未实现 `snapshot` 的渲染器行为不低于一期（仍可走 DOM 序列化）。
- API 变更若改冻结接口，需更新 §0 并说明兼容性（可继续放在 `PLUGIN_API_VERSION = 1` 的可选字段上）。

### 3.4 依赖与风险

| 风险 | 对策 |
| --- | --- |
| 导出与异步 hydrate 竞态 | 导出路径统一 `await pendingHydrates` |
| 快照分辨率 / 主题不一致 | 选项里传 scale、colorScheme |

### 3.5 建议切片

1. 定接口形状（renderer 方法 vs 宿主 API）  
2. export 插件接入等待与替换  
3. echarts 实现 + 单测

## 4. 三期候选 D：`@v5md/core` 新增 AST 节点类型

### 4.1 背景

一期明确不改 core AST。若方案甲（语法 → 伪 code 节点）不够用，才考虑一等公民块节点。

### 4.2 建议范围（开干前必须先 RFC）

- [ ] 定义新节点类型、偏移规则、序列化往返（Markdown ↔ AST）
- [ ] parse / edit / outline / find 全路径适配
- [ ] view 渲染与 Block Renderer 对接方式
- [ ] 迁移与兼容策略（旧文档、旧插件）

### 4.3 验收标准（草案）

- 往返稳定：常见文档 `parse → serialize` 不丢信息。
- 编辑命令（分割块、撤销、粘贴）在新节点上行为有单测。
- 不装对应插件时有合理降级（源码可见或纯文本）。

### 4.4 依赖与风险

破坏面最大：core、所有编辑函数、剪贴板、公众号导出。**默认不进二期排期**，除非 micromark 方案甲被否决。

---

## 5. 三期候选 E：任意 HTML / iframe 自由渲染

### 5.1 背景

一期禁止任意 HTML/iframe，以避免 XSS 与不可控布局。产品若需要嵌入第三方小部件，必须有沙箱模型。

### 5.2 建议范围

- [ ] 仅允许显式 opt-in 的渲染器类型（如 `sandbox: 'iframe'`）
- [ ] iframe：`sandbox` 属性白名单、禁止默认 `allow-same-origin + allow-scripts` 组合除非文档级确认
- [ ] HTML：默认 sanitize（允许标签 / 属性表）；原始 HTML 仅可信插件
- [ ] 预览 void 区内交互与光标 / 拖拽隔离
- [ ] 威胁模型文档（谁可信、谁不可信）

### 5.3 验收标准

- 恶意 `script` / 事件处理器在默认路径下无法执行。
- 官方示例插件（若有）仅演示安全配置。
- 与 Block Renderer 生命周期（destroy 卸 iframe）正确。

### 5.4 依赖与风险

与「远程不可信插件」强相关；无沙箱设计不得合并。

---

## 6. 三期候选 F：远程插件市场与沙箱

### 6.1 背景

`plugin-design.md` 第一阶段不做远程市场；并提到不可信插件将来需要 sanitize / iframe 隔离。

### 6.2 建议范围

- [ ] 插件包签名 / 校验 / 权限清单（可读文档、可改文档、可网络、可工具条…）
- [ ] 加载通道：npm 名、URL、本地路径的安全差异
- [ ] 运行隔离：是否 iframe / Worker；API 表面最小化
- [ ] 卸载与权限回收
- [ ] 市场产品形态不在本仓库也可，但 **SDK 安全契约** 必须先定

### 6.3 验收标准

- 不可信插件无法直接触碰 `innerHTML` 到宿主任意节点。
- 权限拒绝时有明确错误，而非静默失败。

### 6.4 依赖与风险

依赖 E（HTML/iframe 策略）与稳定的 Plugin API 版本策略。工作量偏产品 + 安全，单独里程碑。

---

## 7. 三期候选 G：增量 DOM diff 引擎

### 7.1 背景

一期在「全量 `replaceChildren` 重建壳」前提下，用块实例 `key` 做 reuse。完整增量 diff 是另一条内核级路线。

### 7.2 建议范围

- [ ] 明确目标：降低大文档输入时的主线程耗时 / 闪烁
- [ ] 度量基线：千行文档、含多图表时的输入延迟
- [ ] 可选路径：
  - 只增量更新脏块（仍保留 Markdown 源）
  - 或虚拟列表 / 可视区外不 hydrate
- [ ] 与 Block Host reconcile 的关系：diff 不得绕过 `destroy` / `hydrate` 协议

### 7.3 验收标准

- 有性能对比数据（一期 vs 新方案）。
- 光标、IME、撤销、块插件在回归集上全绿。

### 7.4 依赖与风险

易拖成「重写编辑器」。仅在性能数据证明一期 reuse 不足时启动。

## 9. 推荐排期顺序

```text
二期迭代 1：B match 测试 / 文档对齐（小）
二期迭代 2：C 导出等待 hydrate + snapshot 草案
二期迭代 3：A micromark 挂载点 RFC → 方案甲落地 → 示例扩展
────────── 需要单独立项 ──────────
三期：D AST / E HTML·iframe / F 远程沙箱 / G 增量 diff
```

原则：

1. 先补完已冻结接口（B），再动解析器（A）。  
2. 导出体验（C）可与 A 并行。  
3. D/E/F/G 任一启动前先写短 RFC，更新本文状态与兼容说明。
